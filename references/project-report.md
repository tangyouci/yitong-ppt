# Project report route

Use this route for proposals, stage reviews, leadership or client updates, engineering reviews, delivery reports, roadmaps, and pitches. Optimize for decision clarity, credible progress, and visible evidence.

## Define the decision outcome

Identify the audience, reporting period, project stage, decision needed, exact requirement or milestone language, and which items are achieved, in progress, planned, estimated, or illustrative.

## Default narrative

`objective and value -> current challenge -> overall route -> completed work -> evidence -> milestone progress -> risks and decisions -> next stage -> summary`

For a repeating technical work package, use:

`why the previous result was insufficient -> what changed -> quantitative and qualitative evidence -> progress against the target -> next bottleneck`

## Audience adaptation

- Leadership: challenge, contribution, evidence, value, progress, risk, and requested decision.
- Client: requirement traceability, agreed scope, examples, dependencies, and delivery status.
- Technical review: interfaces, data flow, failure analysis, evaluation conditions, reproducibility, and limits.
- Team execution: ownership, blockers, status, and next actions.

## Useful page archetypes

- Three-part challenge page using real failure scenes.
- System route from input through processing to output and feedback.
- Matched before-and-after evidence with controlled conditions.
- Method adaptation with project-specific change and result.
- Progress dashboard separating achieved, in progress, target, and blocked.
- Risk and decision page with issue, impact, evidence, mitigation, owner, and requested decision.
- Final summary by work package with next action.

## Evidence and status checks

- Put data source, evaluator, scope, tolerance, aggregation, and validation status near each metric when relevant.
- Screenshots demonstrate behavior, not aggregate performance; pair them with measurements when making performance claims.
- Separate feasibility, engineering completion, acceptance, and deployment readiness.
- Report material failures and schedule risks visibly.
- Make the requested decision or next work explicit on the final page.
